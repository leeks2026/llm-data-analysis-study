## 2. 결측·중복·키 품질
- 주요 ID 결측: customers.customer_id, products.product_id, orders.order_id, order_items.order_item_id 모두 0건
- 주요 ID 중복: customers.customer_id·products.product_id·orders.order_id는 0건. order_items.order_id는 464건 중복
- 전체 행 중복: 4개 데이터셋 모두 0건

![결측 중복 점검](images/step02_quality.png)

### 결과 관찰
모든 컬럼의 결측치와 결측 비율은 0이었다. 전체 행 중복도 없었고, 고객·상품·주문의 기본 키는 각각 유일했다. 반면 주문 상세의 order_id 중복은 464건이지만, 한 주문이 여러 상품을 포함할 수 있으므로 자연스러운 결과다.

### 나의 해석과 판단
우선순위는 분석 결과를 직접 왜곡하는 기준 키의 결측·중복, 그다음 금액·날짜·주문상태 같은 핵심 분석 컬럼의 결측과 형식 오류, 마지막으로 전체 행 중복이다. 이번 데이터에서는 즉시 처리할 오류는 없지만 주문 상세의 중복을 오류로 오인해 삭제하지 않도록 주의해야 한다.

### 업무·분석적 의미
기본 키가 유일하고 결측이 없으면 파일 병합과 고객·상품별 집계의 신뢰도가 높아진다. 다만 주문 단위와 주문상품 단위를 구분하지 않으면 정상적인 다대일 관계를 데이터 오류로 잘못 처리할 수 있다.

### 한계와 추가 확인 사항
행 전체 중복이 없다는 사실만으로 중복 주문이나 중복 결제가 없다고 단정할 수는 없다. 주문번호별 동일 상품의 반복 구매가 업무적으로 허용되는지도 확인해야 한다.

## 3. 숫자형·범주형·날짜 점검
- 숫자형 범위에서 주목한 값: age 19 ~ 69세, price와 unit_price 5,000 ~ 200,000원, quantity 1~5개
- 범주형 빈도에서 주목한 값: 상품 카테고리는 7개이며 스포츠 19개로 가장 많고 식품 7개로 가장 적음. 주문 상태는 completed 184건, cancelled 64건, refunded 52건
- 날짜 변환 실패 건수: 0건
- 날짜 범위: 2025-07-09 ~ 2026-07-08

![기본 분포와 날짜 확인](images/step03_distribution.png)

### 결과 관찰
나이는 19 ~ 69세로 분포했고, 상품 가격과 주문 단가의 최소·최대값은 모두 5,000원과 200,000원이었다. 주문 수량은 1 ~ 5개였다. 날짜 변환 실패는 없었으며 약 1년간의 주문 데이터가 포함되어 있다.

### 나의 해석과 판단
가격 범위와 수량 범위만으로 오류 여부를 단정할 수 없다. 상품별 기준 가격표, 할인·쿠폰 적용 여부, 단위(원/천 원), 주문 수량 제한, 고객 연령 수집 규칙을 원천 시스템 또는 업무 규칙과 대조해야 한다. 특히 unit_price와 products.price가 주문 시점에 일치하는지도 추가 확인이 필요하다.

### 업무·분석적 의미
completed 주문은 전체 주문의 약 61%이므로 전체 주문상세를 그대로 매출로 합산하면 취소·환불 건이 포함될 수 있다. 기간은 약 1년으로 월별 비교의 출발점은 될 수 있으나 계절성 판단에는 더 긴 기간이 유리하다.

### 한계와 추가 확인 사항
날짜가 주문 생성일인지 결제 완료일인지 불명확하다. 환불 날짜, 할인액, 배송비, 세금 정보도 없어 순매출이나 실제 인식 매출을 계산하기에는 정보가 부족하다.

## 4. CSV 간 키 관계 검증
- 없는 `customer_id`: 0건
- 없는 `order_id`: 0건
- 없는 `product_id`: 0건

![PK FK 관계 검증](images/step04_relationship.png)

### 결과 관찰
orders의 customer_id, order_items의 order_id와 product_id는 각각 참조 대상 테이블에 모두 존재했다. 따라서 현재 데이터 범위에서는 고객→주문→주문상세→상품의 기본 연결 관계가 유지된다.

### 나의 해석과 판단
키 관계 오류가 있어도 바로 삭제하면 수집 지연, 마스터 데이터 갱신 누락, 삭제된 상품, 시스템 간 코드 체계 차이 같은 원인을 숨길 수 있다. 먼저 오류 행을 별도로 보관하고 발생 위치와 원인을 확인한 뒤, 분석 목적에 맞게 제외·보정·재수집을 결정해야 한다.

### 업무·분석적 의미
키 관계가 유지되면 주문 상세에 상품 카테고리를 붙여 매출을 집계하거나 고객별 주문 이력을 분석할 수 있다. 반대로 키 오류가 있으면 병합 뒤 값이 누락되어 특정 고객·상품의 실적이 과소 집계될 수 있다.

### 한계와 추가 확인 사항
존재 여부만 확인했으므로 참조 키의 유일성, 주문별 주문상세의 누락 여부, 주문상태별 상세 행 존재 여부까지는 검증하지 못했다. 병합 후 행 수 변화도 함께 점검해야 한다.

## 5. LLM 구조 설명 검증
- LLM에 제공한 Safe Context: 파일명, 행·열 수, 컬럼명, 파일 간 키 관계만 제공함
- LLM이 제안한 추가 점검: age 존재 여부와 결측·이상치, customer_id 연결, 매출 계산용 quantity·unit_price 존재 여부, 취소 주문 처리 기준
- 실제 데이터에서 확인한 항목: age 컬럼 존재(True), age 결측 0건, customer_id 연결(True), quantity·unit_price 존재(True)
- 채택/수정/보류한 내용: 구조·결측·키 관계 점검은 채택. 연령대별 매출을 "바로" 분석하자는 제안은 주문상태와 이상치 검토가 선행되어야 하므로 수정. 취소·환불 처리 기준은 보류 후 업무 확인 필요

![LLM 구조 검토](images/step05_llm.png)

### 나의 해석과 판단
가장 유용했던 제안은 분석 아이디어를 실행하기 전 실제 컬럼과 키 관계를 검증하라는 점이다. 가장 조심해야 할 점은 컬럼이 존재한다는 사실만으로 분석이 바로 가능하다고 단정하는 것이다. 예를 들어 age가 있어도 주문상태 처리 기준과 매출 정의가 없으면 연령대별 매출 결과는 달라질 수 있다.

### 한계와 추가 확인 사항
LLM은 제공한 구조 요약을 바탕으로만 답하므로 실제 업무 규칙이나 데이터 생성 과정은 알 수 없다. 원본 데이터 전체나 개인정보를 전달하지 않고, 생성된 제안은 코드와 업무 기준으로 다시 검증해야 한다.
